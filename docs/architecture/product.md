## Platform

web

## Users

xCloud 面向承担核心网日常运行、业务配置与变更治理职责的专业用户：

- NOC 值守与一线运维人员：确认当前网络态势，发现、确认、分派并跟踪告警与异常恢复。
- 核心网运维工程师：管理用户签约数据、配置模板、资费与 OCS 策略，诊断一致性问题并执行受控修复。
- 业务运营人员：观察用户、流量、计费与套餐使用情况，完成批量开通、迁移、导入和导出等运营任务。
- 系统管理员与审计人员：维护 root、operator、viewer 角色边界，处理审批，检查操作记录与变更证据。

这些用户通常在持续运行、信息密度高且操作风险不对称的环境中工作。界面必须帮助他们快速判断状态、影响范围和下一步动作，而不是要求他们先理解实现细节。

## Product Purpose

产品是 **xCloud 电信运营控制台**。

xCloud 的目标是形成一套由自身产品逻辑、工作流和治理能力驱动的电信运营与核心网运维平台。当前产品将用户签约、OCS、资费策略、配置模板、系统健康、审批、告警与审计组织在同一操作环境中，使运营人员能够完成从态势确认、配置变更到结果验证的闭环。

产品成功意味着：用户进入系统后能够快速判断当前运行态势；在变更前看清对象、影响与权限要求；在执行后获得明确、可验证、可追溯的结果；异常发生时能够进入连续的确认、分派、恢复和关闭流程。

## Positioning

xCloud 不是某个开源核心网项目的附属管理页面，也不以复刻 xCloud WebUI 为产品边界。**xCloud 是产品主体和长期演进基石**；xCloud 只是当前阶段使用的开源参考、数据兼容对象和可对接实现之一。

xCloud 的差异化方向，是把电信域对象、实时态势、跨模块变更影响、角色审批、恢复路径与审计证据放入同一套运营工作流。未来可在不改变 xCloud 产品主体的前提下扩展对更多核心网实现、网元与协议观测能力的支持。

## Operating Context

- 当前工作从 Web 控制台进入，支持中文和英文、明暗主题以及键盘命令入口。
- 用户围绕 IMSI、用户签约、配置模板、资费套餐、计费规则、余额、配额、会话、告警和审计记录开展工作。
- 高风险操作需要结合角色权限、审批状态、影响对象、备份或恢复条件以及审计结果进行判断。
- NOC 告警采用“发现 → 确认 → 分派 → 恢复中 → 已恢复”的处置语义。
- 当前数据层使用 MongoDB，并区分核心网/计费业务数据与 xCloud 自有运营数据。
- xCloud 相关字段和数据结构属于当前兼容与参考背景；面向用户的产品叙事、导航和能力归属统一使用 xCloud。

## Capabilities and Constraints

### 当前已实现

- 用户签约记录的查询、创建、编辑、删除、批量创建、导入、导出、策略变更与流量调整。
- 配置模板管理、版本历史与恢复。
- OCS 余额、配额、会话和用量观察，以及资费套餐和计费规则管理。
- 运营分析、系统健康检查、数据一致性扫描与受控修复。
- 告警确认与流转、审批中心、审计日志和变更差异证据。
- JWT Cookie 认证，以及 root、operator、viewer 角色和能力决策。
- 权限感知的统一导航、命令面板、工作区页面和访问保护。
- 中英文界面、明暗主题、响应式 Web 壳层和基础可访问性契约。

### 技术与产品约束

- 当前是基于 Next.js App Router、React、TypeScript 和 MongoDB 的 Node.js Web 应用，不是静态导出产品。
- 服务端鉴权和能力判断是最终安全边界；前端权限感知只用于保持界面与真实权限一致。
- xCloud 自有集合与外部/兼容业务数据必须保持清晰边界，避免产品运营元数据污染核心业务数据。
- 涉及用户、计费、资费、权限和系统修复的变更必须优先保证可验证性、可追溯性和失败恢复说明。
- 不能把路线图能力呈现为已经上线的事实。

### 已确认的未来方向

xCloud 计划逐步向更完整的运营商级核心网监控与运维平台演进。候选方向包括网元管理、网络拓扑、信令与接口监控、性能指标、告警关联、故障定位以及跨网元处置流程，能力广度可参考主流电信设备商的统一运维平台。

上述方向目前属于产品路线图，不代表现有版本已支持特定厂商网元、协议采集、信令追踪深度、SLA 或自动闭环能力。具体支持范围和接入架构仍待后续产品与技术决策确认。

## Product Principles

1. **xCloud 是主体。** 集成对象和开源参考可以变化，产品身份、工作流与能力归属始终属于 xCloud。
2. **态势先于入口。** 用户首先应看懂网络与业务当前是否健康，再决定进入哪个操作模块。
3. **变更必须形成闭环。** 在执行前呈现权限、影响和风险，在执行后提供验证、恢复与审计证据。
4. **专业效率不牺牲一致性。** 快捷键、批量操作和高密度信息必须建立在统一导航、状态和交互契约上。
5. **愿景与现状严格分开。** 面向未来的网元、信令与运营商级运维能力可以指导架构，但不能提前包装成已交付功能。

## Accessibility & Inclusion

xCloud 的核心任务必须能够通过键盘和辅助技术完成。表单需要持久名称和明确错误关联；表格排序、选择和操作需要可感知语义；Dialog 必须约束并恢复焦点；状态变化不能只依赖颜色。中英文模式下可访问名称与可见文案应保持语言一致。
